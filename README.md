# dot-muncher 吃豆游戏

- 项目地址：https://github.com/JCXYOZH/dot-muncher
- 在线演示：http://setup.cc.cd



## 一、功能说明

### 玩家
- 昵称 + 内部 UUID 双重标识：界面只显示昵称，同名玩家互不冲突；未来联机时 UUID 可"认领"为账号。
- 创建 / 切换 / 改名 / 删除均有操作；删除玩家会连带清理其全部存档与检查点（有二次确认）。
- **游客兜底**：无玩家时开始游戏，自动创建"游客"（重名自动编号），进度绝不丢失，之后可在玩家页改名转正。

### 存档（手动）
- 游戏进行中会实时把**关卡中途快照**（豆子残余矩阵、玩家像素坐标与朝向、4 只幽灵的位置/朝向/状态/虚弱倒计时）写入检查点（localStorage `dm.checkpoint`）。
- 存档页的表单读取该检查点存为手动档：**可精确恢复到吃到一半的瞬间**，不降级为"关卡起点"。
- 同名存档会弹确认层询问是否覆盖；每玩家上限 20 份手动档，达上限会引导清理。
- 支持导出 / 导入 `.json` 文件（单份或全部），跨浏览器 / 跨设备迁移存档；导入逐份校验，重名自动加"· 导入"后缀，坏数据跳过并计数提示。

### 存档（自动）
- **通关必存**：每过一关自动写入"下一关起点"型自动档（游戏画面右上角轻量 HUD 角标提示，不打断游玩）。
- **离页兜底**：切页 / 切标签页 / 关闭页面时，把进行中的快照升格为自动档。
- **失败续档**：生命耗尽 GAME OVER 时，自动存"本关开头"（得分回退到本关开始值防止刷分，生命回满 5），下一局可从该关重来。
- 自动档独立滚动槽位，最多保留最近 3 份，**永不覆盖玩家命名的手动档**；内容相同时仅刷新时间，避免槽位抖动。

### 读档
- "继续当前进度"卡片：接上次离开（含崩溃恢复）的精确状态。
- 任意手动 / 自动档均可"读取并开始"：恢复后进入**暂停态**（画面显示 PAUSE），按空格正式开始，防止恢复瞬间被幽灵偷袭。
- 已通关玩家在读档页显示"已通关"徽章（战绩来自玩家数据，非存档）。

### 数据安全
- 每份存档带 djb2 校验和，并额外校验“能否安全恢复”：豆子矩阵必须严格为 31×28、玩家/幽灵坐标必须落在地图内、目标格与朝向/状态/倒计时必须是合法值。手改或损坏的存档会被标记"已损坏"并以灰色隔离展示，**可删除但不可读取**，不影响其他存档。
- 存档结构带 `schemaVersion` 版本号 + 迁移注册表：未来加字段不炸旧档。
- 多标签页通过 `storage` 事件总线实时同步，玩家 / 存档列表跨页签自动刷新。
- localStorage 不可用（隐身模式 / 被禁）时优雅降级：页面显示提示条，游戏本身照常可玩。

## 二、数据结构（localStorage 键）

```
dm.players          = [{ id(UUID), name, createdAt, lastActiveAt,
                         stats: { gamesStarted, bestScore, cleared } }]
dm.activePlayerId   = "<UUID>"
dm.saves.<玩家UUID>  = {
    __v: 1,
    saves: [{
        id, name, slotType: 'manual'|'auto',
        level, score, lives,
        remark,               // 备注（选填，最长60字，空则不落字段，无此键亦兼容）
        snapshot: { beans, player:{x,y,orientation}, ghosts:[{...}] } | null,
        isCheated,            // 仅数据，任何界面均不展示
        schemaVersion: 1, sum: "<校验和>",
        createdAt, updatedAt
    }]
}
dm.checkpoint       = { playerId, level, score, lives, isCheated, snapshot, updatedAt }
sessionStorage dm.pendingLoad = { playerId, save }   // 读档页 → 游戏页 同标签页交接
```

单份存档约 1.5KB；20 手动档 + 3 自动档 / 玩家，远低于 localStorage 约 5MB 配额。

## 三、内部调度键

游戏进行中按 **Ctrl + Shift + L** 直接跳至下一关（供调试使用，第 12 关接着按下进入通关结算）。

- 界面、控制台、任何提示中均**不出现**该键的任何痕迹；代码中键值以 `(188-112)` 形式计算，注释中性化。
- 使用过调度键的本局，其产生的所有存档（含自动档）会带 `isCheated: true` 数据标记，同样**任何界面不展示**，提供作为后续数据清洗或者未来联机校验。

## 五、联机预留架构

- **存储适配层**：所有读写都经过 `dm-core.js` 中的统一 `store` 接口（get / set / remove）。未来联机时实现同接口的远端适配器（REST 或 WebSocket）并替换即可，游戏逻辑、三个页面**零改动**。
- **自包含负载**：检查点与待读档都是完整数据包，未来可直接作为服务端中继的状态同步载体（主机权威模式）。
- **快照可扩展**：`snapshot.player` 为单玩家结构，未来双人游玩时升级为 `snapshot.players[]`，通过 `schemaVersion` 迁移函数平滑升级旧档。
- **玩家 UUID 认领**：本地玩家未来注册账号时可把 UUID 映射为账号 ID，老存档无缝跟随。

## 六、项目概述

### 6.1 主题与设计目的

`dot-muncher` 是一个纯前端吃豆游戏，主题是“经典街机玩法 + 现代本地存档体验”。设计目的有三个：

1. **可玩**：完整实现移动、吃豆、能量豆、幽灵追击、生命、计分、12 关与结算。
2. **可续**：用 `localStorage` 做玩家、手动档、自动档、检查点，解决“关掉页面就从头开始”的真实痛点。
3. **可维护**：不引入框架和构建工具，按页面 / 样式 / 脚本 / 图片 / 字体分层；游戏引擎与存档系统解耦，便于演示和后续联机扩展。

### 6.2 目标用户

- 想利用碎片时间随时玩一局经典吃豆游戏的普通用户；
- 学习观察“原生 JavaScript + Canvas + localStorage”的完整实现过程；
- 实现演示动态网站、DOM 操作、表单验证、响应式布局等场景

### 6.3 页面数量与相应功能

项目共有 6 个 HTML 页面：

| 页面 | 路径 | 主要功能                              |
| --- | --- |-----------------------------------|

## 七、功能模块说明

### 7.1 游戏页：从启动到结算

1. **启动页**：Canvas 绘制吃豆图标、标题与闪烁提示；按 Enter 或空格进入第 1 关。
2. **关卡循环**：每关用二维数组描述墙、通道和幽灵巢穴；玩家吃到全部豆子后 `game.nextStage()` 进入下一关。
3. **移动**：方向键或 WASD 设置 `player.control.orientation`；玩家到达格子中心才允许转向，避免穿墙。
4. **吃豆**：玩家所在格有豆时 `_SCORE++`，豆子矩阵置 1；能量豆让所有正常/虚弱幽灵进入虚弱状态 450 帧。
5. **碰撞**：玩家与幽灵距离平方小于 750 时判定接触；正常幽灵触发 30 帧死亡动画并扣命，虚弱幽灵被吃掉加 10 分并回巢。
6. **暂停**：关卡布景 `status` 在 1（运行）与 2（暂停）之间切换；暂停时仍绘制画面，但不更新对象。
7. **结算**：生命耗尽进入结算页，显示最终得分（豆子分 + 剩余生命奖励）；按 Enter/空格重开。

### 7.2 玩家页：昵称 + UUID

- 创建时 `normalizeName` 做控制字符清理、trim、12 字截断，再检查非空与重名。
- 界面只显示昵称；所有存档、检查点、当前玩家键都使用 UUID，因此同名玩家不会串档。
- 删除玩家会二次确认，并连带删除其 `dm.saves.<UUID>` 与属于该玩家的检查点。
- 当前玩家被删除时，自动切换到最近活跃的其他玩家；没有其他玩家则清空活动 ID。
- 无玩家时开始游戏会自动创建游客，保证进度不丢。

### 7.3 存档页：手动档与自动档隔离

- 手动档：玩家命名，最多 20 份；同名时弹确认层选择覆盖；卡片内的“导出”只导出该条记录。
- 自动档：系统滚动保留最近 3 份；通关、离页、失败续档时写入，永不覆盖手动档。
- 当前进度卡片读取 `dm.checkpoint`，保存的是“关卡中途精确快照”，不是关卡起点。
- 损坏档灰显隔离，可删除但不可读取；底部“导出全部存档（N 份）”只统计通过校验的有效档，损坏档不会混入。

### 7.4 读档页：恢复、转存、导入

- “继续当前进度”读取检查点，恢复后进入暂停态，按空格开始。
- 任意手动/自动档都可“读取并开始”；自动档可“转存”为手动档，避免被滚动淘汰。
- 支持单文件与多文件导入；先校验文件级 magic/version，再对 `saves[]` 中的每一份重新迁移、校验 checksum 和可恢复语义，重名自动加“· 导入”后缀。
- 一个“全部存档”文件里即使只有部分记录损坏，合法记录仍会导入，损坏记录逐份跳过；汇总提示会列出前 3 份的名称与原因。

### 7.5 项目页与关于页

- 项目页用 CSS Grid 三列卡片展示项目，移动端降为单列；卡片整块可点击，内部“查看项目”保留原生链接。
- 关于页用引言 + 卡片分区组织内容；邮箱字段由第三方解码脚本还原，避免明文抓取。

## 八、技术实现细节

### 8.1 游戏引擎：Game / Stage / Map / Item

`static/script/game.js` 是一个约 400 行的轻量引擎，核心抽象如下：

| 对象 | 职责 | 关键方法 |
| --- | --- | --- |
| `Game` | 管理 canvas、布景队列、主循环、事件表 | `start` / `stop` / `setStage` / `nextStage` / `getPosition` |
| `Stage` | 一个场景（启动页/关卡/结算页），管理地图与对象 | `createItem` / `createMap` / `resetItems` / `resetMaps` / `bind` |
| `Map` | 二维地图、坐标转换、BFS 寻路 | `get` / `set` / `coord2position` / `position2coord` / `finder` |
| `Item` | 可绘制可更新的实体（玩家/幽灵/文本） | `bind` / `update` / `draw` |

主循环使用 `requestAnimationFrame`，并限制最小帧间隔 16ms，避免高刷新率屏幕把游戏速度放大。每帧顺序为：

```text
清屏 -> stage.update() -> 每张 map.update/draw -> 每个 item.update/draw -> 下一帧
```

### 8.2 幽灵寻路：BFS + 隧道 + 幽灵互斥

`Map.finder` 使用广度优先搜索：

1. 用 `steps[y][x]` 记录“是否访问”和“来源坐标”；
2. 每层从当前节点向上下左右扩展；
3. 地图外坐标按 `(x + x_length) % x_length` 取模，实现左右隧道；
4. 找到终点后从终点沿来源回溯，得到最短路径；
5. 幽灵正常状态使用 `type:'next'` 只取下一步，虚弱状态随机选路径，回巢状态以初始坐标为目标。

为避免四只幽灵重叠，每只幽灵寻路时会复制地图，并把其他正常幽灵所在格临时标为墙。这个处理只在幽灵到达格子中心时执行，减少每帧计算。

### 8.3 地图绘制：按邻居生成墙线

墙体不是贴图，而是根据当前格上下左右是否有墙生成线段/圆角：

- 先判断四个方向 `code[0..3]`；
- 组合为 `1100 / 0110 / 0011 / 1001` 时画圆角；
- 其他组合按方向画直线；
- 墙地图 `cache:true`，引擎第一帧绘制后缓存为 `ImageData`，之后每帧直接贴图。

豆子地图不能缓存，因为会被吃掉，因此每帧重绘；能量豆用 `3 + times % 2` 的半径做闪烁。

### 8.4 存储适配层与事件总线

所有业务读写都经过 `dm-core.js` 的 `store`：

```js
store.get(key)        // 读取并 JSON.parse
store.set(key, value) // JSON.stringify 后写入
store.remove(key)
store.available       // 启动时探测 localStorage 是否可用
```

未来联机时，只需实现同接口的远端适配器，页面与游戏逻辑不需要改动。事件总线把“存储变化”转成业务事件：

- `players:changed`
- `active:changed`
- `saves:changed`
- `checkpoint:changed`

本页操作直接 `emit`；其他标签页通过 `window.addEventListener('storage', ...)` 触发同名事件，实现多标签页同步。

### 8.5 校验和与版本迁移

每份存档写入前计算 djb2 校验和：

```js
h = 5381
for each char: h = ((h << 5) + h + charCode) | 0
```

校验时排除 `sum`、`createdAt`、`updatedAt`，因此“只刷新更新时间”的自动存档不需要重算内容摘要。读取旧档时先走 `migrateRecord`，按 `schemaVersion` 逐级迁移；缺少版本号的远古数据按 v1 处理。

### 8.6 检查点、快照与恢复

游戏页每 150ms 检查一次状态：

- 分数 / 生命 / 关卡变化时立即写检查点；
- 否则每 2 秒兜底写一次；
- 死亡动画期间不采集，沿用上一份有效快照。

快照包含：

```js
{
  beans: [[...]],                       // 豆子残余矩阵
  player: { x, y, orientation },        // 玩家像素坐标与朝向
  ghosts: [{ x, y, orientation, status, timeout, vector }]
}
```

恢复时先 `game.setStage(level)` 把关卡重置到干净状态，再用快照覆盖豆子、玩家、幽灵，最后把布景设为暂停态，避免出现“读档后幽灵立刻贴脸”的问题。

### 8.7 自动存档滚动槽位

自动档使用 3 个滚动槽位，逻辑在 `autosave`：

1. 新记录置顶；
2. 只保留最近的 3 条 `slotType === 'auto'`；
3. 如果最新自动档的关卡、分数、生命、作弊标记、完整快照都相同，则只刷新 `updatedAt`，不新增槽位；
4. 手动档永远不参与裁剪。

### 8.8 DOM 渲染、XSS 与事件委托

- 列表使用 `map(...).join('')` 生成 HTML，减少多次 DOM 插入；
- 所有用户可控文本经过 `esc()`（`& < > " '`）；
- 弹层结构固定，但标题/正文用 `textContent` 写入；
- 列表按钮使用 `data-act` + `data-id`，在 `document` 上做事件委托，重绘后无需重新绑定；
- 表单统一使用 `submit` 事件，同时覆盖鼠标点击与 Enter。

### 8.9 表单验证

| 场景 | 校验函数 / 位置 | 规则 | 反馈 |
| --- | --- | --- | --- |
| 创建玩家 | `validatePlayerName` | 非空、去控制字符、12 字截断、重名检查 | 输入框下方错误 + toast |
| 改名 | `CORE.renamePlayer` | 非空、排除自己的重名检查 | 行内错误 + toast |
| 保存存档 | `CORE.normalizeName` / `addSave` | 名称可空（用建议名）、备注 60 字、手动档上限 20 | 表单错误 + toast |
| 导入存档 | `CORE.importData` | magic、version、checksum、快照结构、自动档跳过、上限 | 汇总 toast |

### 8.10 BOM / 浏览器 API 使用

## 十、实现原理

### Q1：为何用原生 JavaScript？

作为练习 JavaScript 基础、DOM 操作、BOM、事件与表单验证。原生实现能完整展示这些能力，也避免构建工具把代码“藏”起来。项目通过 IIFE 隔离作用域、事件总线和存储适配层控制复杂度；若未来接入框架，`DM.CORE` 的接口可以原样复用。

### Q2：游戏主循环为什么用`requestAnimationFrame`加 16ms 限频？

`requestAnimationFrame` 会跟随浏览器刷新节奏，在标签页隐藏时自动暂停，比 `setInterval` 更省电。但 120Hz/144Hz 屏幕回调频率更高，如果每帧都按固定速度移动，游戏会变快；因此在回调里比较时间戳，距上一帧不足 16ms 就跳过逻辑更新，保证不同屏幕上速度一致。

### Q3：玩家移动为什么不会穿墙？

玩家使用 `location.position2coord` 把像素坐标换算成地图格子坐标，并带一个 `offset` 表示离格子中心的距离。只有 `offset` 为 0（到达格子中心）时才接受新的方向；接受前还会检查目标方向 `map.get(x+cos, y+sin)` 是否为墙。这样转向只能发生在路口，不会斜着穿墙。

### Q4：幽灵是怎么追玩家的？

`Map.finder` 使用广度优先搜索。每只幽灵到达格子中心时：

1. 复制地图，把其他正常幽灵所在格标成墙，避免叠在一起；
2. 以玩家当前格为终点做 BFS；
3. 正常状态取路径下一步，虚弱状态随机选一条可行分支，回巢状态以初始坐标为目标；
4. 得到下一步坐标后设置 `vector`，再按方向移动。

BFS 保证每一步都是最短路径，使幽灵“聪明地围堵”而不是乱走。

### Q5：吃豆和能量豆是怎么判定的？

玩家站在格子中心且 `beans.get(x,y) === 0` 时：

- 普通豆：`_SCORE++`，把该格设为 1（已吃）；
- 能量豆：先判断 `config.goods[x+','+y]`，再把所有 `status` 为 1/3 的幽灵设为 3（虚弱）并重置 `timeout=450`。

豆子地图与墙体地图分离，墙体缓存，豆子每帧重绘，所以吃掉后立刻消失。

### Q6：碰撞检测为什么用距离平方？

判定条件是 `dx*dx + dy*dy < 750`。真实距离需要 `Math.sqrt`，而平方比较与开方单调等价；每帧对 4 只幽灵计算，省掉开方可以减少不必要的浮点运算。750 约等于 27px 的接触半径，和 30px 的角色尺寸匹配。

### Q7：暂停是怎么实现的？

引擎的 `Stage.status`：`1` 正常运行、`2` 暂停、`3` 死亡动画。按空格/Enter 在 1 和 2 之间切换；主循环在 `stage.status == 1` 时才更新对象，但仍然绘制，所以画面静止且能看到 `PAUSE` 字样。暂停时不会写入错误的中间态检查点。

### Q8：生命、得分和通关奖励怎么算？

吃一颗普通豆 +1 分，吃虚弱幽灵 +10 分；初始 `_LIFE=5`。被正常幽灵抓到后进入 30 帧死亡动画，动画结束扣 1 条命并重置本关对象；生命为 0 进入结算。最终得分 = `_SCORE + 50 * max(_LIFE-1, 0)`，即每条剩余备用命奖励 50 分。HUD 显示的是“备用生命”，所以初始显示 4 个。

### Q9：检查点为什么不是每帧写？

每帧写 `localStorage` 会造成主线程卡顿和配额浪费。游戏页用 150ms 观测循环，只有分数、生命、关卡变化或距上次写入超过 2 秒时才写；死亡动画期间不采集。这样既接近实时，又把写入频率控制在每秒最多几次。

### Q10：存档里的“中途快照”包含什么？

`dmCapture()` 采集三部分：

- `beans`：豆子残余二维矩阵；
- `player`：玩家像素坐标与朝向；
- `ghosts`：4 只幽灵的坐标、朝向、状态、虚弱倒计时和目标 `vector`。

恢复时先 `setStage(level)` 得到干净关卡，再用快照覆盖这些字段，最后设为暂停态。这样能精确回到“吃到一半”的瞬间，而不是关卡起点。

### Q11：为什么读档后要暂停？

读档瞬间玩家和幽灵的位置来自快照，如果直接运行，幽灵可能已经在玩家旁边，玩家来不及反应。把 `stage.status` 设为 2 后，画面显示 PAUSE，玩家准备好再按空格开始，体验更佳。

### Q12：自动存档为什么不会把手动档冲掉？

手动档 `slotType='manual'`，自动档 `slotType='auto'`。`autosave` 只裁剪 `slotType==='auto'` 的记录，手动档不参与；手动档上限 20 份，自动档固定 3 个滚动槽位。两类数据在 UI 上也分开展示。

### Q13：自动存档怎么避免槽位抖动？

写入前比较最新自动档与新记录的关卡、分数、生命、作弊标记和完整快照；全部相同则只更新 `updatedAt`，不新增记录。这样玩家在原地停留、反复触发 `pagehide` 时，不会很快把 3 个槽位占满。

### Q14：存档损坏是怎么发现的？

分两层检查：

1. **完整性**：每份存档写入前计算 djb2 校验和 `sum`，读取时重新计算并比较，发现内容被改动；
2. **可恢复性**：`recordDataError()` 与 `isValidSnapshot()` 检查关卡/分数/生命是否为合法整数，豆子矩阵是否严格 31×28，玩家和幽灵像素坐标是否位于画布地图范围，幽灵目标格 `vector` 是否在 0..27 / 0..30 内，以及朝向/状态/倒计时是否越界。

仅重算 checksum 不能绕过第二层。读取列表、导出全部、导入三个入口共用同一套规则；损坏档仍然展示，但只允许删除，不允许读取/转存，也不会进入导出文件。

### Q15：如何实现的新版加字段旧存档依旧有效？

存档带 `schemaVersion`，读取时走 `migrateRecord`，按版本逐级执行迁移函数。缺少版本号的旧数据按 v1 处理；迁移函数抛错时保留原记录并停止继续迁移，页面会把它标记为损坏而不是崩溃。

### Q16：导出的 JSON 为什么能跨浏览器迁移？

导出文件包含 `magic`、`version`、`player`、`saves` 和每份存档的 `sum`，是一个自包含负载。单档导出固定写入 `saves: [save]`；全部导出只收集同时通过 checksum 与语义校验的记录。导入时逐份重新校验并生成新的 ID/时间戳，因此不依赖源设备的 localStorage；重名会自动加“· 导入”后缀。

### Q17：为什么玩家需要 UUID，不能只用昵称？

昵称允许修改，也可能重复；如果用昵称做存储键，改名或重名会串档。UUID 在创建时生成，之后不变；界面只显示昵称，逻辑层始终用 UUID。未来联机时还可以把 UUID 认领为账号 ID。

### Q18：localStorage 不可用时怎么办？

启动时做一次写入-删除探测，失败则 `store.available=false`。页面显示提示条，所有写操作返回失败，但游戏本身仍可玩；不会因为存储异常白屏。读取失败/JSON 损坏也统一返回 `null`。

### Q19：多个标签页同时打开会怎样？

每个页面订阅 `players:changed` / `active:changed` / `saves:changed` / `checkpoint:changed`。本页写入后直接 `emit`；其他标签页通过浏览器 `storage` 事件触发同名事件，列表自动刷新。删除/覆盖操作都有确认层，避免误操作。

### Q20：用户昵称里写 `<script>` 是怎么避免被执行的？

所有昵称/备注/存档名在拼入 `innerHTML` 前都经过 `esc()` 转义；弹层标题/正文使用 `textContent`。项目页的项目名通过 `textContent` 写入，不经过 HTML 解析。

### Q21：表单为什么用 `submit` 事件？

原按钮用 `click`、输入框用 `keydown` 判断 Enter，两个入口容易不一致。改成 `<form>` + `submit` 后，鼠标点击、键盘 Enter、辅助技术触发表单提交都走同一条路径，并且可以统一 `preventDefault` 阻止页面刷新。

### Q22：响应式主要做什么？

- 内容区 `max-width:1000px` 居中；
- 800px 断点下导航压缩、项目卡片单列、玩家/存档行换行；
- 游戏画布 `max-width:100%; height:auto`，保持 3:2 比例；
- 按钮、输入框在窄屏占满可用宽度；
- 长文本使用 `overflow/text-overflow/white-space` 防止撑破布局。

### Q23：项目用了哪些 Array / String 方法？

- Array：`map`、`filter`、`some`、`find`（部分兼容写法用 `filter()[0]`）、`forEach`、`sort`、`slice`、`concat`、`indexOf`；
- String：`trim`、`slice`、`replace`、`indexOf`、`charAt`、`toLocaleString`（时间）、`toString(36)`；
- 典型组合：`list.filter(...).sort(...).map(...).join('')` 完成“筛选 → 排序 → 渲染”。

### Q24：为什么游戏页用轮询识别开局/终局，而不是改引擎事件？

轮询只依赖 `game.getIndex()` 与公开的布景数组，不侵入引擎内部状态机；引擎未来替换时，存档接线仍可复用。150ms 的轮询开销很小，而且能同时完成检查点节流写入。

### Q25：如果未来做双人联机，现有结构如何复用？

- `store` 适配层换成 REST/WebSocket 实现；
- 检查点和待读档本身就是完整数据包，可作为主机权威状态同步载体；
- `snapshot.player` 升级为 `snapshot.players[]`，通过 `schemaVersion` 迁移；
- 玩家 UUID 映射账号 ID，老存档继续跟随；
- Nginx 增加 `/ws/` 反向代理即可。

### Q26：卡片内“导出”和底部“导出全部存档”有什么区别？

- “导出”绑定当前卡片的存档 ID，导出数组只有这一项，文件名形如 `dot-muncher_存档名.json`；
- “导出全部存档（N 份）”汇总当前玩家的所有有效手动档和自动档，N 是实时计算的有效档数量，文件名为 `dot-muncher_玩家名_存档.json`；
- 两者使用相同的 `magic/version/player/saves` 结构，读档页都按“逐份校验”的同一路径处理。

### Q27：导入“全部存档”文件时如何实现逐份检查的？

当文件级检查通过后，`importData()` 遍历 `saves[]`，每条记录都重新执行 `migrateRecord → recordDataError → checksum`，并单独生成新的 ID。某一份失败只把该份计入 `skipped/invalid`，不会中断其余记录；汇总 Toast 会显示“成功几份、跳过几份”，并列出最多 3 份无效档的名称和原因。

### Q28：背景的浅蓝波浪动效具体怎么实现的？

它不是 GIF，也不是逐帧图片，而是“浅蓝渐变底图 + 内联 SVG 波形 + CSS 视差动画”三层叠加：

1. **铺浅蓝底图。** `index.html` 的 `.mod-bg` 通过 `background: url('../image/public/bg.svg') center top / cover repeat-x` 引入 `static/image/public/bg.svg`。这个 SVG 用线性渐变和径向渐变叠加出白色到浅蓝的柔和底色，容器宽 `100%`、高 `600px`，位于页头背景层。
2. **定义一条可复用的波形。** `.mod-bg` 内联了一个 `viewBox="0 24 150 28"` 的 SVG，核心路径是：

   ```html
   <path id="gentle-wave"
         d="M-160 44c30 0 58-18 88-18s58 18 88 18 58-18 88-18 58 18 88 18 v44h-352z">
   </path>
   ```

   其中 `c`、`s` 是三次贝塞尔曲线命令，连续生成多个波峰和波谷；末尾的 `v44h-352z` 把曲线向下封口，形成一条可以填充的波浪带。
3. **叠加四层半透明白波。** 四个 `<use>` 都复用 `#gentle-wave`，共同使用 `x="48"`，纵向偏移分别为 `y="0/3/5/7"`，填充透明度分别为 `0.4/0.6/0.2/1`。位置错开、透明度不同，单条曲线就变成了有纵深的浪花。
4. **用不同速度制造视差。** `.parallax>use` 统一执行 `move-forever`：在 `translate3d(-90px,0,0)` 与 `translate3d(85px,0,0)` 之间循环。四层动画时长依次是 `7s/10s/13s/20s`，延迟依次是 `-2s/-3s/-4s/-5s`。负延迟让动画从周期中段开始，四层不会同步；速度不同则形成近快远慢的视差。
5. **按容器宽度横向拉伸。** `.waves` 宽度为 `100%`、贴在 `.mod-bg` 底部，高度限制在 `80px~120px`；`preserveAspectRatio="none"` 允许 SVG 横向拉伸。`viewBox` 从 `y=24` 开始，只取下方 `28` 个单位，避免绘制上方无用区域。位移使用 `translate3d`，浏览器可以放到合成层处理，减少布局重排。

### Q29：各关墙体如何绘制，并区分圆角与直线？

墙体不是每一关单独导出的图片，而是通过定义二维数组作为“墙线骨架”，在 Canvas 上根据相邻格自动接线。

**1. 二维数组到画布坐标**

- 每一关的 `config.map` 是 `31` 行 × `28` 列的数组，`0` 表示通路，`1` 表示普通墙，`2` 表示幽灵巢穴墙。
- `Map` 默认一格 `size=20px`，地图左上角为 `(60,10)`。`coord2position(i,j)` 把格坐标换算成格中心：`x = 60 + i*20 + 10`，`y = 10 + j*20 + 10`。后续圆弧和直线都以格中心为基准。
- 同一份关卡数据会创建两块地图：墙地图设置 `cache:true`，只画一次；豆子地图负责每帧重画剩余豆子。两者分离，墙体不会因为豆子被吃掉而重复遍历。

**2. 计算四位连接码**

对每一个非零墙格，先建立：

```js
var code = [0, 0, 0, 0]; // 依次表示 右、下、左、上
```

然后检查四个相邻格。以右侧为例：

```js
if (this.get(i + 1, j) &&
    !(this.get(i + 1, j - 1) && this.get(i + 1, j + 1) &&
      this.get(i, j - 1) && this.get(i, j + 1))) {
    code[0] = 1;
}
```

意思是：右边确实是墙，同时当前格不是被周围墙体完全包住的内部格，才把对应位置 `1`。下、左、上三个方向按同样思路旋转判断。这样墙带内部不会重复落笔，只有需要接线的转角或边才会进入绘制逻辑。

**3. 两位组合画四分之一圆，其他组合画直线**

`code.join('')` 恰好是以下四种组合时，代码用 `context.arc()` 画圆角，把两个相邻方向平滑接起来：

| `code.join('')` | 置位的相邻方向 | 圆心相对格中心 | Canvas 角度 | 效果 |
| --- | --- | --- | --- | --- |
| `1100` | 右、下 | `(+10,+10)` | `180°→270°` | 右侧与下侧之间的圆角 |
| `0110` | 下、左 | `(-10,+10)` | `270°→360°` | 下侧与左侧之间的圆角 |
| `0011` | 左、上 | `(-10,-10)` | `0°→90°` | 左侧与上侧之间的圆角 |
| `1001` | 上、右 | `(+10,-10)` | `90°→180°` | 上侧与右侧之间的圆角 |

其他组合（单方向、对向、T 形或十字形）进入 `default` 分支。程序遍历 `code`，对每个置位从格中心画一段到格边的直线：

```js
var dist = this.size / 2;
context.moveTo(pos.x, pos.y);
context.lineTo(pos.x - _COS[index] * dist,
               pos.y - _SIN[index] * dist);
```

`_COS = [1,0,-1,0]`、`_SIN = [0,1,0,-1]` 分别对应右、下、左、上。需要特别注意：当前用的是减号，所以实际直线端点位于索引方向的反侧；进行阅读或重构这段代码时不能仅凭方向名把减号改成加号，否则会改变现有地图的接线效果。

**4. 颜色与缓存**

- 描边宽度固定为 `2px`；普通墙使用关卡配置的 `wall_color`，幽灵巢穴的 `value===2` 改用白色。
- 墙地图开启 `cache:true`。引擎第一次绘制后调用 `getImageData(0,0,960,640)` 保存整张画布，后续帧直接 `putImageData()` 贴回，而不是重新执行 `31×28` 的双层循环和几十次圆弧/直线绘制。
- 豆子、玩家和幽灵仍逐帧绘制在缓存墙体之上，因此画面会更新，但静态墙体只需计算一次。

### Q30：启动页标题居中、版权右下、提示闪烁和吃豆人张嘴动画怎么实现？

启动页是 Canvas 中的一个独立 `Stage`，内部坐标固定为 `960×640`。CSS 只负责等比缩放画布，因此下面的坐标在桌面和手机上都保持相同比例。

**1. 标题居中**

游戏名使用一个 `Stage Item`：

```js
x: game.width / 2,
y: game.height * 0.5
```

绘制时同时设置：

```js
context.textAlign = 'center';
context.textBaseline = 'middle';
context.fillText('Dot-Muncher', this.x, this.y);
```

`x=480` 是水平中心，`textAlign='center'` 让文字从中心向两侧展开；`y=320` 是垂直中心，`textBaseline='middle'` 让文字基线也对齐中心。三者共同保证标题真正位于画布中央，而不是左上角对齐。

**2. 版权信息贴右下角**

版权文字不是写死坐标，而是先设置字体，再用 `measureText()` 测量真实宽度：

```js
var text = '© setup.cc.cd';
this.width = context.measureText(text).width;
this.x = game.width - this.width - 10;
this.y = game.height - 20 - 5;
```

- `game.width - 文字宽度 - 10`：右边缘始终留 `10px` 间距。
- `game.height - 20 - 5`：底部留出约 `25px` 空间，配合 `textBaseline='top'` 让文字顶部从该位置向下绘制。
- 该 Item 绑定了 `click`，点击后用 `window.open()` 打开本人 GitHub 页面。

**3. “Press Enter to start” 闪烁**

这个 Item 设置 `frames:28`。引擎每 28 个游戏帧更新一次 `item.times`，而主循环用 `16ms` 限频，所以约每 `0.45s` 切换一次：

```js
if (this.times % 2) {
    context.fillText('Press Enter to start', this.x, this.y);
}
```

`times` 为奇数时绘制、偶数时跳过，形成显示约 `0.45s`、隐藏约 `0.45s` 的闪烁。监听 `keydown` 后，`Enter`（键码 `13`）和空格（键码 `32`）都会调用 `game.nextStage()` 进入第一关。

**4. 黄色吃豆人的张嘴/闭嘴循环**

标题上方的黄色吃豆人由 Canvas 直接绘制，而未使用图片，通过设置：

```js
frames: 3,
draw: function(context) {
    var t = Math.abs(5 - this.times % 10);
    context.beginPath();
    context.arc(
        this.x, this.y, this.width / 2,
        t * 0.04 * Math.PI,
        (2 - t * 0.04) * Math.PI,
        false
    );
    context.lineTo(this.x, this.y);
    context.closePath();
    context.fill();
}
```

- `frames:3` 让动画每 3 帧更新一次；`times % 10` 产生 `0~9` 的循环。
- `t = |5 - times%10|` 的序列是 `5,4,3,2,1,0,1,2,3,4...`，因此嘴巴会平滑地从最大张开程度收拢到闭合，再重新张开。
- `t=5` 时圆弧从 `0.2π` 画到 `1.8π`，留下 `72°` 的开口；`t=0` 时从 `0` 画到 `2π`，变成完整圆形（闭嘴）。
- 圆弧最后通过 `lineTo(圆心)` 和 `closePath()` 补成扇形再填充，所以可以使缺掉的那一块看起来像是嘴巴；另画一个黑色小圆作为眼睛。

最后，`PressStart2P` 字体通过 `FontFace` 异步加载。加载成功后才执行 `game.init()`；加载失败则在 `catch` 中直接初始化，保证字体不可用时游戏仍能启动。标题和版权之所以先设置字体再 `measureText()`，是为了让文字宽度、居中位置和右下角对齐都基于实际显示字体计算。

### 11.4 性能与体验优化

- **帧率稳定**：主循环使用 `requestAnimationFrame`，并限制为约 16ms 一帧，避免高刷新率屏幕让角色速度翻倍。
- **静态地图缓存**：墙体在一局中不变，绘制一次后缓存为 `ImageData`；豆子地图仍逐帧绘制，因为会被吃掉。
- **存储写入节流**：检查点每 150ms 观测一次，只在关卡/分数/生命变化时写入，否则每 2 秒兜底一次，不按帧写 localStorage。
- **自动档去重**：相同内容只刷新 `updatedAt`，避免反复离开页面把 3 个槽位快速耗尽。
- **DOM 批量更新**：列表使用 `filter → sort → map → join` 一次性写入，避免逐条插入造成多次重排。
- **事件委托**：玩家/存档/读档按钮统一在 `document` 上监听，重绘后无需重新绑定。
- **减少不必要计算**：碰撞用距离平方代替开方；寻路只在格子中心触发；BFS 队列逐层扩展。
- **交互反馈**：保存、覆盖、删除、导入、读档均有 Toast；破坏性操作有自定义确认弹层，支持 Esc 与遮罩取消。

### 11.5 兼容与降级

- `localStorage` 启动时做写入/删除探测；不可用时页面提示，但游戏仍可运行。
- `sessionStorage` 写入或读取失败时返回 `null`，读档流程不会把游戏页卡死。
- 字体加载失败、`FontFace` 缺失时仍启动游戏；画布字体回退到系统字体。
- 旧浏览器缺少 `scrollTo` 时，回到顶部回退为直接设置 `scrollTop`。
- 导入文件先校验 JSON、magic、version、checksum、数值范围与快照结构；任一环节失败只跳过该份记录。

### 11.6 尚未实现的扩展

- 移动端目前保证浏览、玩家管理和存档管理可用；游戏操作仍以键盘为主，尚未加入虚拟方向键。
- 没有音效/背景音乐；游戏逻辑暂不依赖音频资源。
- 没有 Service Worker，因此不是可离线安装的 PWA。
- 跨设备同步需要导出/导入 JSON；真正的账号云同步属于“联机预留架构”的后续工作。

## 十二、总结与反思

### 12.1 主要收获

1. **把游戏规则拆成数据与行为两层**：12 关只维护矩阵与能量豆坐标，移动、碰撞、吃豆、幽灵寻路统一由规则层处理，新增关卡不需要复制逻辑。
2. **理解了“可恢复状态”比“保存分数”复杂**：真正的中途存档必须同时保存豆子残余、玩家位置/朝向、幽灵位置/状态/倒计时与目标点。
3. **认识到存储系统需要防御性设计**：checksum、版本迁移、重名处理、损坏档隔离、槽位去重，比单纯的 `JSON.stringify` 更接近真实产品。
4. **原生 JavaScript 也能形成清晰架构**：游戏引擎、业务规则、存储核心、页面控制器、公共 UI 分层后，没有框架也能保持可读性。
5. **测试要覆盖失败路径**：空输入、重名、坏 JSON、损坏 checksum、存储失败、无效关卡等边界场景，比只看“正常流程”更容易发现真实问题。

### 12.2 遇到的困难

- **幽灵寻路**：直接把整张地图交给 BFS 会出现幽灵重叠；最终在每次寻路时把其他幽灵所在格临时视为墙，并只在格心重新计算路径。
- **隧道坐标**：越界坐标不能简单判墙，需要取模后映射到另一侧，同时保留“是否发生环绕”的标记。
- **读档后的状态一致性**：读档不能只改分数，必须先把目标关卡重置到干净状态，再覆盖快照，最后强制暂停，避免幽灵贴脸。
- **自动存档抖动**：早期只比较“有没有快照”，导致离开页面时同一关卡反复占槽；改为完整内容比较后解决。
- **表单体验**：按钮 click、输入框 keydown、浏览器原生 submit 混用容易出现双提交或状态不同步，统一为 form submit 后逻辑明显更稳定。

### 12.3 后续改进

- 增加触屏虚拟方向键与手势暂停，让移动端也能完整游玩。
- 增加 Web Audio 音效与音量开关，并记住用户偏好。
- 将静态资源版本化，加入 Service Worker 做离线缓存。
- 在远程 `store` 适配器上实现账号登录、云存档与冲突合并。
- 增加自动化回归脚本并纳入 CI，持续验证创建玩家、存档、导入、读档和游戏关键路径。
